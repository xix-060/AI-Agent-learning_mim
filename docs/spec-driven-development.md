# Spec 驱动开发 vs Vibe Coding

## Vibe Coding（氛围编程）
- 直接跟 AI 说"帮我做个 XX"，它写啥用啥
- 不看代码，报错就把错误贴给 AI
- 优点：快，零门槛
- 缺点：代码失控、无法维护、坑了自己
- 适合：一次性脚本、Demo、个人小工具

## Spec 驱动开发（Spec-Driven Development）
- 先写详细规格书（SPEC.md），AI 按规格实现
- 人负责规格和验收，AI 负责实现
- 优点：可控、可测试、可维护
- 缺点：前期投入多 30 分钟
- 适合：正经项目、团队协作、长期维护的代码

## 对比表
| 维度 | Vibe Coding | Spec 驱动 |
|---|---|---|
| 前期投入 | 0 | 30-60 min |
| 代码质量 | 看运气 | 可控 |
| 可维护性 | 差 | 好 |
| 验收标准 | 感觉 | 明确的 checklist |
| 适合场景 | Demo/脚本 | 生产项目 |

## Spec 驱动核心流程
1. 写 SPEC.md（人）—— 定义做什么、不做什么、验收标准
2. AI 读 Spec 出实现计划
3. AI 分步实现，每步对照验收标准
4. 人按 checklist 验收
5. 不符合 → 打回重做（引用 Spec 条目）

## 返工次数对比：Vibe vs Spec

> 返工 = 一次产出没过验收，需要回炉改。数字为典型观察值，非硬保证。

| 阶段 | Vibe 流程 | Spec 流程 |
|---|---|---|
| 首次产出 | AI 直接写代码 | AI 按 Spec 分步实现 |
| 报错循环 | 报错→贴给 AI→改→又报错，常 3-5 轮 | Spec 已约束边界，报错少 |
| 跑偏修正 | AI 自由发挥，常偏题需整段重写 | 偏了引用 Spec 条目定点改 |
| **平均返工次数** | **3-8 次** | **0-2 次** |
| 返工原因 | 需求没说清、AI 猜错、上下文丢失 | Spec 有缺口或边界情况没覆盖 |
| 累计耗时 | 看着快，越改越慢（上下文越拖越脏） | 前期慢，后期省（返工少） |

**关键差异**：Vibe 的返工是"猜→错→再猜"的循环，每次返工上下文都更脏，AI 容易引入新 bug；Spec 的返工是"对照清单查漏补缺"，改动局部、不扩散。

## Spec 流程下 AI 一次通过率

"一次通过" = 首次产出就过验收、无需返工。

| 任务复杂度 | 一次通过率 | 说明 |
|---|---|---|
| 简单（单函数、脚本） | ~70-80% | 边界少，Spec 写清 AI 基本能过 |
| 中等（多文件、有依赖） | ~40-60% | 最常见，偶有边界情况需 1 次微调 |
| 复杂（跨层、新架构） | ~15-30% | 难一次过，但返工次数仍远低于 Vibe |

**为什么 Spec 一次通过率也不是 100%？**
1. Spec 本身有缺口（人没想到的边界情况）
2. AI 对模糊表述的解读与人不同
3. 外部依赖行为（API 返回格式、库版本差异）难在 Spec 完全枚举

**提高一次通过率的杠杆**：
- 验收标准写得可测（"返回 list[dict]，长度≥1"而非"返回合理结果"）
- 边界情况显式列出（空输入、超长输入、并发）
- 给 AI 反例（"不要做 X"比"做 Y"更省返工）
- 关键接口先定 schema，再写实现

> 一句话：Spec 不保证一次过，但把"赌运气"变成"查清单"——通过率从 Vibe 的 ~20% 提到中低复杂度的 50%+，且失败时改的是局部不是整体。

## 一句话总结
Vibe Coding 是"让 AI 开车我睡觉"，Spec 驱动是"我定目的地和路线，AI 开车我看路"。
