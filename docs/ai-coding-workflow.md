# AI 写 Web 应用的实战记录

## 项目

个人 Todo 应用（Flask + SQLite + 原生 JS 单页）

---

## 人机分工

### 总体原则

| 角色 | 职责 |
|------|------|
| **人** | 定需求、审方案、验收、手动测试、判断方向对不对 |
| **AI** | 出方案草案、写代码、写测试、修 Bug、做 Code Review |

人不需要写大量代码，但 **每一步必须验收**，不能一次性让 AI 生成全部。

---

### 分步分工（5 步流程）

#### 第 1 步：方案设计

| | |
|---|---|
| **AI 做** | 输出目录结构、数据库表设计、RESTful 路由、前端页面结构 |
| **人做** | 审核方案是否合理（表设计、路由命名、技术选型），确认后再写代码 |
| **验收** | 方案通过，不启动编码 |

> 本次确认项：独立 `todo_app/` 目录、PATCH 更新、`description` 字段、端口 5000。

---

#### 第 2 步：后端实现

| | |
|---|---|
| **AI 做** | 先写 `tests/test_api.py`，再写 `db.py` + `app.py`（TDD） |
| **人做** | Review 代码结构，运行 `pytest tests/test_api.py -v` 验收 |
| **验收** | 13 个测试全绿 |

> 本次 AI 自测发现 1 个测试逻辑写反（pending 筛选），自行修复后全绿。

---

#### 第 3 步：前端实现

| | |
|---|---|
| **AI 做** | 写 `templates/index.html`（原生 JS fetch + CSS 单页） |
| **人做** | 浏览器打开手动测试 4 个功能：添加、完成、筛选、删除 |
| **验收** | 4 项功能手动走通 |

---

#### 第 4 步：修 Bug

| | |
|---|---|
| **AI 做** | 根据复现步骤定位并修复，补充对应测试 |
| **人做** | 实际用一遍，把问题 + 复现步骤反馈给 AI |
| **验收** | 原 Bug 场景测试通过 |

> 本次预设 Bug（空标题 500、删除后不刷新）在第 2/3 步已提前实现，手动测试未发现新问题，跳过。

---

#### 第 5 步：自查 Review

| | |
|---|---|
| **AI 做** | 检查 SQL 注入 / XSS、错误处理完整性，列出 3 个改进点（只列不改） |
| **人做** | 阅读 Review 结论，决定哪些改进值得做 |
| **验收** | Review 报告输出 |

## 经验教训

1. **先方案后代码** — 避免方向错了白干一整轮
2. **分步验收** — 测试全绿 / 手动走通才进下一步，不要一次性生成全部
3. **TDD 有效** — 先写测试再写实现，AI 也能遵循这个顺序
4. **Bug 反馈要具体** — 说清楚复现步骤，AI 修得准
5. **安全要主动问** — AI 不会主动做安全 Review，第 5 步要明确要求
6. **网络环境要提前说明** — 例如 HN 爬虫改用 Algolia API，避免反复超时排查

## 参考：标准 Prompt 模板

### 第 1 步（出方案）

```
@folder 我要做一个 XXX 应用。技术栈：Flask + SQLite + 原生 HTML/JS 单页。
先不要写代码。请给出：
1. 目录结构
2. 数据库表设计
3. API 路由设计（RESTful）
4. 前端页面结构
等我确认后再写代码。
```

### 第 2 步（后端）

```
方案确认。现在实现后端：
1. app.py：Flask 应用 + 所有路由
2. db.py：SQLite 封装
3. 先写 tests/test_api.py（pytest + Flask test client）
先写测试再写实现。
```

### 第 4 步（修 Bug）

```
有两个问题：
1. [具体现象 + 期望行为]
2. [具体现象 + 期望行为]
请修复，并给这两个场景补测试。
```

### 第 5 步（Review）

```
现在 review 整个项目：
1. 检查安全问题（SQL 注入、XSS）
2. 检查错误处理是否完整
3. 给出 3 个可以改进的点（只列出不改）
```
