# Simon Willison AI 编程经验提炼

> 来源：Anthropic《Claude Code: Best practices for agentic coding》。
> 一切最佳实践都围绕一个约束：**上下文窗口会填满，LLM 性能随上下文变满而下降**——上下文是最该管理的资源。

## 核心原则

### 1. 探索优先（Explore, Plan, Code, Commit）

先让 AI 读代码库探索 → 输出计划 → 确认后再写码 → 小步提交。Plan Mode 把"探索"和"执行"分开，避免 AI 直接动手解错问题。

- Explore：Plan 模式只读不改，问"这段代码怎么处理 session/登录"
- Plan：让 AI 出实现计划，可手改后再继续
- Implement：回 Normal 模式按计划写码、写测试、跑测试
- Commit：描述性提交信息 + PR

> 小任务（一句话能描述的 diff：改错别字、加日志、重命名）跳过计划直接做。计划适合：不确定方法、跨多文件、不熟悉的代码。

### 2. 写 SPEC 文件（同 Day 3 Spec 驱动）

CLAUDE.md / 规则文件就是给 AI 的"持久规格书"——每会话自动加载，存项目知识。

- ✅ 写：AI 猜不到的命令、偏离默认的风格、测试说明、仓库礼仪、环境怪癖、易踩的坑
- ❌ 不写：读代码能知的、标准约定、易变信息、"写干净代码"这种废话
- 准则：每行问"删了它 AI 会犯错吗？"，不会就删。太长会被忽略。

### 3. 给 AI 验证自己工作的手段（最高杠杆）

让 AI 能自检：跑测试、对比截图、校验输出。没有验收标准，AI 会产出"看着对其实错"的东西，你成了唯一反馈环。

- 给可测验收："写 validateEmail，例：<user@example.com>→true，<user@.com>→false，写完跑测试"
- 治本不治标：贴报错，让 AI 修根因而非压制错误
- 这是**单点收益最高**的一条

### 4. 用截图 / 富内容

UI 问题给截图比文字描述有效 10 倍。可用 `@` 引文件、贴图、给 URL、管道输入（`cat error.log | claude`）。让 AI 对比结果图和原图、列差异、修。

### 5. 控制上下文

新会话有干净上下文，别让一个会话干到 token 爆炸。一次调试/探索就能吃掉数万 token，上下文越满 AI 越健忘越犯错。用自定义状态行监控用量，半满就开新会话。

### 6. 频繁 git 提交

AI 改坏了随时回滚。每阶段末尾提交，描述性信息。

### 7. CLAUDE.md / 规则文件（项目知识沉淀）

项目知识沉淀成规则文件，跨会话共享。可放多级目录（家目录、项目根、父/子目录）。提交进 git 让团队共享，文件价值随时间复利增长。

## 反模式（不要学）

- **一次对话做 10 件事**：上下文快速爆炸，AI 健忘犯错。拆成多个小会话，每个聚焦一件事。
- **不看 diff 直接接受所有修改**：你放弃了反馈。每次看 diff，像 review 同事代码。
- **让 AI 修它自己看不懂的错误**：先自己复现、贴完整报错和涉及文件——AI 看不见的代码改不了。给症状 + 可能位置 + "修好长啥样"。

## 我的适配（Trae / Cursor 用户）

| Claude Code 概念 | Trae / Cursor 对应                               | 我的实操                                |
| -------------- | ---------------------------------------------- | ----------------------------------- |
| CLAUDE.md      | `.trae/rules/*.md`（已建 project.md/agent-dev.md） | 规则文件存项目知识，frontmatter 控生效范围         |
| Plan Mode      | Trae Plan 模式 / Cursor Composer 规划              | 复杂任务先 Plan，一句话 diff 直接做             |
| 权限许可           | Trae 权限模式 / Cursor 审批                          | lint/git 放开，写文件/装依赖保留审批             |
| 给 AI 验证        | `tests/` + 跑脚本自检                               | 如 lora\_train 的 `smoke` 分支：改完跑一小段验证 |
| 截图富内容          | Trae 粘贴图片 / `@` 引文件                            | UI bug 直接截图贴，比描述强                   |
| 上下文管理          | 一个会话干一件事，满了开新会话                                | 长任务用 subagent 隔离上下文                 |
| 频繁提交           | git 小步提交                                       | 每个可运行单元提交一次                         |

**我的转化口诀**：

1. 规则文件 = 给 AI 的"项目说明书"（已建 `.trae/rules/`）
2. Plan 模式做规划，Normal 模式写码
3. 给验收标准 + 让 AI 自检（跑测试/脚本）
4. 一个会话一件事，token 半满就开新会话
5. 每个可运行单元提交，回滚不心疼

> 对照本周实战：lora\_train 改 logger 时——先 Plan（方案2 改代码+冒烟）、给验收（logger 格式+不重复）、让 AI 自检（跑 `smoke` 看输出）、小步提交。正是 Explore→Plan→Code→Commit 的缩影。

## 多智能体协作开发的实验结论

- PM→开发→测试分工有效，规格质量明显提升
- 但 LLM 测试员会"放水"：口头 PASS ≠ 代码能跑
- 必须有真实执行环节（跑代码/跑测试）兜底
- 结论：AI 角色分工 + 真实 CI 验证 = 可靠；纯 LLM 自评 = 不可靠
